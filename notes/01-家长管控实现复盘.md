# 01 · 家长管控实现复盘

> 对应规格：`docs/PARENTAL.md`。本文只记录"为什么这么做"和真机上验证出来的结论，不重复规格内容。

## 一、需求的起点

上游 Aerial 是没有家长管控的桌面。二次开发要加的是三件事：**每天能看多久、一次能看多久、两次之间歇多久**，到点锁屏，家长输密码才能延长。

最开始的设计是"一个统一的总时长限制"。后来发现这在真实家庭里几乎用不起来：周一到周五孩子只有少量时间，周末却有大把时间，一个固定数字两边都不合适。这个矛盾后来引出了「基础额度 + 做题赚取」的新方案（见 `notes/04`）。

## 二、两条计时口径，而不是一条

这是整个模块最重要的一个决定。

| | 记账口径（默认） | 发时间口径（严格模式） |
|---|---|---|
| 时间归谁 | 归孩子，观察屏幕 | 归家长，一次性发放 |
| 依据 | 播放信号是否在播 | 一张有时长的票 |
| 停在视频 App 首页 | 不计时 | 照常计时 |
| 代价 | 依赖设备能不能报准播放状态 | 每次要看，家长都得在场发票 |

实现上，`ParentalClock` 每秒读一次信号，严格模式下用 `WatchTicket.counting()` 覆盖读数；其余情况用 `PlaybackSignal.read()` 的结果。两种口径共用同一个 `WatchTimer`，所以限额、锁屏、密码延长这些逻辑没有分叉。

**教训**：不要试图造一个"既准又不用家长在场"的口径。这两者本质冲突，做成可切换的两套，比做一套折中的更清楚。

## 三、播放信号：三级降级 + 有界三值判定

理想信号是 `MediaSessionManager.getActiveSessions()` 里的 `PLAYING` 会话。但真机上这条链路经常不可用，所以设计了三级降级：精确会话 → 前台 App 包名 → 设备使用时长兜底。

真机上发现一个容易被误判的情况：**小米 MiTV-MFTP0（Android 9）在极光播放时，`dumpsys media_session` 仍报 0 个会话**。也就是说"会话列表可读但恒为空"是这台设备的固件事实，不是权限没配好，也不是代码没拿到通知监听权限。

最初的实现把"空列表"当成"暂停"，于是这台电视上计时器**一秒都不走**。修法是引入 `SessionVerdict`：把一次采样判成三值——**在播 / 没在播 / 不知道**。

- 空列表本身不能下结论；只有先确认"这台设备的会话列表是可读且可信的"，才允许把空解释成没在播。
- 判为"不知道"时保持上一次读数，不擅自归零，也不擅自累加。

**教训**：传感器返回值里的"空"和"不可用"是两件事。把它们合并成一个 `false`，是这类信号驱动逻辑最常见的 bug。

## 四、计时器必须活在进程里，不是界面里

最初的一秒轮询写在 Home 的 `LaunchedEffect` 里。真机实测：把极光放到前台 50 秒，`dailyUsed` 是 0。

原因不是协程被取消，而是 **Compose 的延迟任务要等下一帧才恢复；窗口不可见时根本没有下一帧**。而"视频 App 在前台"恰恰是唯一需要计时的时刻——计时器在最需要它的时候停了。

改成挂在进程上的 `Handler` 循环（`ParentalClock`），每秒 `postDelayed` 自己。`start()` 做成幂等，因为 App 启动和 Home 组合两处都会调，两个时钟会把每一秒算两遍。

## 五、两个时钟要分开

| 用途 | 用哪个钟 | 为什么 |
|---|---|---|
| 累计时长 | `SystemClock.elapsedRealtime()` | 开机起算，用户改不了系统时间 |
| 判断"今天" | `System.currentTimeMillis()` 的本地日期 | elapsedRealtime 重启归零，没法表示日期 |
| 间隔倒计时落盘 | 墙钟 | 倒计时要在进程死掉/重启后接着走 |

`WatchTimer` 内部只用 elapsedRealtime；`ParentalStore` 保存进度时把倒计时截止点换算成墙钟。两者只在**同一时刻取一次差值**时发生关系，所以改系统时间最多让一次倒计时早结束或晚结束，**不能刷新当天额度**。

已知的宽松点（规格里也写了）：进程没跑的那段不算观看（`MAX_TICK_MS = 60s`），断电重启最多丢 30 秒（`SAVE_EVERY_MS`）。对家庭场景够用。

## 六、四个真机缺陷（都是上机之后才发现的）

1. **守护轮询从未启动**：`HomeGuardService` 的前台检查以"有没有设密码"为前置，而 `Parental.hasPin` 要等 `ParentalStore` 读完才有值。时钟 init 之后补了一次 `onParentalReady()` 回调才把守护唤醒。
2. **`lastWindow?.first == launchedGuest` 双 null 早退**：两边都是 null 时表达式为真，闸门在最不该退的时候退了。加 `launchedGuest != null` 前置。
3. **视频 App 自拉首页盖掉闸门**：这类 App 切后台会自己拉起首页 Activity，把密码页顶到后面。`GateActivity.onPause` 后 250ms 重新置顶，最多 4 次。
4. **票在前台不动时过期不拦**：严格模式下，孩子停在同一个 App 不动，票到期了也没人重新判闸门。改成每轮用 `lastKnownFront` 判，而不是只在"前台发生变化"时判。

**教训**：这四条没有一条能靠单元测试发现，全是"状态没变化时要不要重新判"的问题。守护类逻辑的测试用例里一定要有「什么都不动，只是时间过去」这一条。

## 七、密码与失败锁定

密码是 8–12 位纯数字（遥控器只有数字键和方向键）。存的是带 scope 前缀的哈希，比较用 `MessageDigest.isEqual` 做定长比较。

`Attempts` 单独成文件，不放在 `ParentalStore` 里：它防的是"孩子坐在电视前一直猜"，这个状态必须**扛得住强制停止 App 和重启**，所以落盘的是墙钟截止时间。规则是连续 5 次错误关闭 5 分钟，期间输对也拒绝；`leftSec` 对等待时长做了上限截断，把系统时间往回调不会把 5 分钟变成几小时。

管理员恢复口令属于私密信息，**不入库、不进 APK 明文**：由 `local/admin.properties` 在构建期注入 `BuildConfig`，`local/` 已被 `.gitignore` 排除。没有该文件的检出里 `ADMIN_HASH` 为空，恢复路径自动失效。相关单测通过 `AERIAL_ADMIN_PHRASE` 环境变量驱动，源码里不放任何形式的口令（明文、hex 都不放）。

## 八、测试策略

- **纯逻辑层可单测**：`WatchTimer`、`AttemptState`、`SessionVerdict`、`Limits`、`WatchTicket` 都不碰 Android，喂数字就能跑，规格里的验收用例用等价断言覆盖。
- **Android 侧只有一个入口**（`PlaybackSignal.AndroidSource`），判定逻辑本身不碰系统，可在单测里喂任意答案。
- **真机自检**：`tools/selftest.sh` 配合 `ParentalProbe` 暴露测试入口（置额度、发票、清票、读状态），能自动跑到"看 N 秒 → 额度涨 N 秒 → 到点锁屏"。
- **自检要能复原**：`resetToday()` / `restoreDay()` 成对，跑完把真实计数器放回去，不在电视上留下测试痕迹。

## 九、明确管不到的（别让家长误会）

- HDMI / DTMB 直播：信号源是固件层的事，软件拦截不了。
- 待机、关机、拔电源、恢复出厂。
- 关闭无障碍守护后，按 HOME 会回到原桌面。
- 手机投屏是否计入，取决于投屏 App 是否在"视频类 App"白名单里，需要逐台确认。

规格文档里把这些写进了用户可见的部分，这是对的——管控类功能最怕家长误以为"设了就等于管住了"。
