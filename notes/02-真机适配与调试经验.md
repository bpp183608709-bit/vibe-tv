# 02 · 真机适配与调试经验

> 各机型的具体限制和解法在 `docs/devices/`（20 余篇），性能结论在 `docs/PERF-2026-10-28.md`，交接规则在 `docs/HANDOFF.md`。本文只记跨机型通用的方法论和反复踩到的坑。

## 一、先确认"能不能读到"，再谈"读到的是什么意思"

国产电视的 Android 层差异极大，同一个 API 在不同固件上的表现可以完全相反。适配时不要假设：

- `MediaSessionManager.getActiveSessions()` 在部分小米固件上**恒为空**，即使在播视频。
- 有些厂商不允许安装声明 `CATEGORY_HOME` 的应用（因此才有 `guard` 这个不带 HOME intent 的 flavor，靠无障碍服务接管）。
- 通知监听权限、后台启动 Activity 权限、无障碍服务开关，各家入口和默认值都不同。

**方法论**：把"这个信号在这台设备上是否可用"做成一个可观测的事实（写进日志、进自检脚本），再决定要不要降级。不要靠 `if (list.isEmpty())` 这种代码去猜设备能力。

厂商特殊处理优先写成**按功能检测**（某个包是否存在、某个设置项是否存在），并在注释里写明在哪台机型验证过；只有确实检测不出来，才落进 `DeviceProfile` 按机型硬编码。

## 二、ADB 批量脚本的两个坑（macOS / zsh）

这两条在一次批量禁用操作中各浪费了一轮排查：

1. **zsh 默认不对变量做单词切分**。`for p in $PKGS` 会把整个字符串当成一个包名，循环只跑一次，且 `pm` 会悄悄忽略多余参数，看起来像"执行了但没报错"。改用逐行 `while IFS= read -r p`，或显式 `set -o shwordsplit`。
2. **adb 会吞掉循环的 stdin**。用 `while read < file` 驱动 `adb shell` 时，循环第二次就断了——`adb` 把输入流读走了。每个 `adb` 调用都要加 `< /dev/null`。

```sh
while IFS= read -r p; do
  adb -s "$TV" shell "pm disable-user --user 0 $p" < /dev/null
done < /tmp/pkgs.txt
```

## 三、`dumpsys diskstats` 不能用来结算回收量

一次清理里，`dumpsys diskstats` 的 `App Size / App Data Size / App Cache Size` 在执行前后**完全一致**，即使 `df` 显示多出了 15 GB。这三个数字是系统缓存的估算值（包含预分配块），由 storaged 周期性刷新，不会因刚刚删除文件而更新。

某批操作按它估算应回收 846 MB，`df` 实测只有 92 MB。

**结论**：磁盘回收一律以 `df` 的前后差值为准；`diskstats` 只适合做"哪个包占得多"的相对排序。

## 四、Compose 与后台窗口

- `LaunchedEffect` 里的延迟任务依赖下一帧，窗口不可见时没有下一帧，等于停止。需要"App 在后台也要每秒跑"的逻辑必须挂在进程上（`Handler` / 前台服务），并做成幂等启动。
- 锁屏是一个独立的 `singleInstance` + `excludeFromRecents` Activity，自己吃掉返回键/菜单键，`setShowWhenLocked`，进来先结束屏保。它**不计数**，只每秒走一次截止判定，额度一解除就让路。
- Android 10+ 从后台启动 Activity 需要 `SYSTEM_ALERT_WINDOW`；没授予时只能靠主屏自己的轮询把锁屏拉起来，从第三方视频 App 里可能顶不出来。安装脚本里要主动授予，并且每 2 秒重试 + 留诊断日志。
- 守护在锁屏期间要特判：平时 `isDefaultHome()` 时主动放行 HOME，锁屏期间必须拦，否则按 HOME 就把锁屏顶掉了。

## 五、界面与文案

- 画布按 **960×540dp** 统一缩放，不要按真实 dpi 计算。
- 遥控器可按的控件统一用 `Pressable`，只在"本控件上开始的按压"抬起时触发；否则长按打开菜单时那次抬起会误触菜单第一项。
- 焦点问题要单独验：曾报"确认键选不上"，最后确认是恒可聚焦，属于焦点样式/视觉反馈问题，不是 focusable 配置问题。
- 五语文案（`values` / `values-zh` / `values-ru` / `values-uk` / `values-kk`）条数一致、占位符一致、`*强调*` 标记一致，脚本校验过再打包，`aapt2 dump` 确认 APK 内五种语言俱在。
- 手机配置页的文字放在 `KEYS` / `TEXTS` 表里，脚本里不要写死中文。

## 六、构建与发布

| 约定 | 原因 |
|---|---|
| JDK 17、Compose BOM 锁在 1.9 | Compose 1.10+ 要求 minSdk 23，工程要覆盖 Android 5.0 |
| `standard` / `guard` 两个 flavor | 部分国产固件拒绝安装声明 HOME 的包 |
| 签名密钥放 `local/`，不入库 | 电视只接受首次安装时那把钥匙签的更新包，换钥匙就装不上 |
| 上机一律用 release 版 | debug 版在电视上会卡 |
| 上机后 `cmd package compile -m speed -f app.orchard.tv` | ART 编译后才是真实性能表现 |
| 发 TCL 版本前 `versionCode` 加 1 | 该渠道的更新检测依赖它 |

签名配置由 `app/build.gradle.kts` 在 `local/signing.properties` 存在时读取，否则回落到本机 debug key——**能装新机，但不能覆盖已有安装**。管理员恢复口令也用同一套注入机制。

## 七、诊断要能从日志独立回答

家长时钟每一秒打一行，除了状态变化时打，每 10 轮也打一次，行里带 `watching` / `level` / `front` / 未取整的 `used` / 当前 ticket 剩余秒数。

这样做的好处是：出现"这个 App 到底算不算在看"这类问题时，**从 logcat 就能回答，不用截电视的图**。真机上正是靠它发现"极光在前台 50 秒，`dailyUsed` 为 0"的。

## 八、未验证过的不要写"已完成"

工程约定里专门列了一条：没有在真机上验证过的功能，不要说已完成。规格文档的阶段记录里区分了「已写」/「Kotlin 已编译、单测已跑」/「真机 PASS」，这三种状态不是一回事。
