## 3. 证书与端口：一个进程，三个监听（2026-11-17 定稿）

原本这里写的是「Python 只监听 127.0.0.1，nginx 在前面按端口分流」。**实现时取消了 nginx**：

```bash
python -m server.app.api \
    --listen 0.0.0.0:8443:/opt/wrong-quiz/tls/h5.pem:/opt/wrong-quiz/tls/h5.key \
    --listen 0.0.0.0:9443:/opt/wrong-quiz/tls/server.pem:/opt/wrong-quiz/tls/server.key \
    --listen 127.0.0.1:8100
```

一个进程多绑几个 socket，每个 socket 带自己的证书。理由：代理要买的是「TLS 集中、限速、静态缓存」，
而 TLS 在这套设计里本来就只是「两个端口两套证书」，限速在配对接口里，静态文件只有三个；
换来的却是第二个要监控、要重启、要写配置的守护进程。等真需要多机/灰度/HTTP2 时再加，
那时它是升级而不是返工。

**每个端口都服务全部路由。** 原本计划按端口裁剪（电视口不放行 `/v1/h5/*`），实现时没做：9443 用的是
只有电视信的那张私有 CA，别人连 TLS 都握不上手，裁剪能防的东西本来就不在威胁模型里；而多一层
「这个端口放行哪些路径」的规则，就会多一类「443 上能用、8443 上 404」的怪问题。

| 端口 | 证书 | 给谁 | 说明 |
|---|---|---|---|
| 8443 | Let's Encrypt 的 **IP 证书**（SAN 只有 `IP:47.95.198.148`），160 小时、自动续期 | 家长手机 | 手机不再警告。**手机只能打这个端口** |
| 9443 | 自签 CA 的新叶子（`CN=quiz.qust.me`，签发者 `Aerial Quiz CA`） | 电视 | 手机打开**必弹**「证书不受本机信任」；电视钉的就是这张 CA，换 CA 要重装 APK |
| 443 | 同 8443 的 LE 证书 | 家长手机（备案下来后加） | 加一行 `--listen`，代码不改 |
| 8100 | 无 TLS，只听 127.0.0.1 | 本机 curl / 探活 / 运维脚本 | 不对外 |
| 22 | — | 运维 | 只放行你的固定 IP |

几件容易踩的：

- **手机打开家长页只能用 `8443`，用 `9443` 一定弹警告。** 9443 那张是我们自己 CA 签的，只有 APK 里内置了
  这张 CA 的电视才认，安卓/iPhone 都会说「证书不受手机操作系统信任」，必须点一次「继续访问」才进得去。
  而且因为每个端口都服务全部路由，**打错端口页面照样能打开**——这正是它容易被误用的原因。
  （2026-11-17 踩过一次：以为公信证书没生效，其实是把 9443 存成了书签。）
- **端口 8443 + Let's Encrypt 是备案期间的正解。** 证书公信力与端口无关，手机浏览器不会报警；8443 不受
  「未备案域名 80 端口拦截」影响。备案下来后加一条 `--listen 0.0.0.0:443:…`，地址从 `:8443` 变成默认 443，
  代码一行不改。
- **电视不校验域名，只校验 CA**（`QuizHttp.kt` 里 `HostnameVerifier { _, _ -> true }`）。所以新叶子的 SAN
  写 `quiz.qust.me` 就够，**CA 不换 = 已装机的电视不用重装**。但 `baseUrl` 变了，APK 仍然要重出一次。
- **LE 续期用 `certbot renew` + `--deploy-hook "systemctl restart wrong-quiz"`**。没有 nginx 可 reload，
  而这个进程是启动时读证书的：忘记重启的典型症状是「证书明明续上了，浏览器还在报过期」。顺手把续期
  和重启写进同一条 cron/timer，不要靠人记得。

| 设备鉴权 | ✅ `device.secret_hash` + Bearer | 10 条新验收全是「试图冒充别人」，全部被拒 |
| 部署件 | ✅ systemd / 备份 / 探活 / runbook | 备份 64 KB、探活三项全绿、恢复演练逐表对上行数 |
| 端口与证书 | ✅ 8443 / 9443 / 8100 loopback | 外部可达；8443 仍是自签，等备案后换 LE |

**在真 MySQL 上抓到两个只有真 MySQL 才有的 bug**（SQLite 全绿，207/207 掩盖了它们）：
关掉 autocommit 时一条普通 SELECT 会留下一个 REPEATABLE READ 事务，之后这条连接上所有读都停在
「上一次请求结束」那一刻——手机记的错题对下一组题不可见；以及事务内的读没有做 `datetime → 文本`
归一化，暂停窗口因此把第六次错答当成第一次。两个都是「静默地给错答案」，这是这类适配 bug 里最贵的。
所以 §4.1 那句「这条不是形式」应当留着：**它当时是对的。**

### 4.1 范围

1. **真 MySQL 上把 `schema.sql` 跑通。**
   空机装 MySQL 8.0 → `mysql < server/db/schema.sql` → 逐条修错 → 导入知识树与种子题 →
   `check_schema_parity.py --mysql` 直接比真库与 SQLite。
   然后给 `acceptance.py` 加 `--dsn`，**在 MySQL 上把 207 条跑一遍**。这条不是形式：现在 207 条证明的是
   SQLite 能用，而生产是 MySQL，两边的差异（`?`→`%s`、`ON UPDATE CURRENT_TIMESTAMP`、`JSON` 列、
   严格模式下的 `TINYINT` 溢出）只有真跑才知道。
2. **电视端设备鉴权。**
   `device` 表加 `secret_hash CHAR(64)`；`/v1/pair/start` 一次性返回 `device_secret`（32 字节随机，
   电视存进自己的 prefs，不再上送明文）；电视此后每个请求带 `Authorization: Bearer <secret>`；
   `api.py` 在分发前统一校验（`/v1/pair/*` 与 `/v1/quiz/*`、`/v1/quota`、`/v1/config`、`/v1/heartbeat`）。
   失败返回 401 `bad-device`。**旧的、没有 secret 的请求一律拒绝**——家里那台电视跟着 M1 的新 APK 一起换。
3. **部署件与运维。**
   `deploy/` 全套（§1.3）、`deploy/env.example`、`systemd` 开机自启与重启策略、nginx 限速
   （`/v1/auth/login` 与 `/v1/h5/pair` 各 5r/m burst 10）、`daily backup` + **恢复演练一次**（把备份恢复到
   staging 库并查行数，不做演练的备份等于没有备份）。
4. **安全组**：只开 22（你的 IP）/ 8443 / 9443 / 443，其余全关。MySQL 只监听 127.0.0.1。

### 4.2 验收

```bash
curl -s https://quiz.qust.me:8443/health           # 200，且不暴露版本与 DSN
mysql -N -e "select count(*) from information_schema.columns where table_schema='quiz'"   # 215
.venv/bin/python server/tools/check_schema_parity.py --mysql "$QUIZ_DSN"                  # 0 处差异

### 4.3 风险

真 MySQL 上大概率还有第三、第四处 DDL 问题（唯一键长度、`ENUM` 默认值、外键字符集）。预留一天专门修，
不要和别的事混在同一个改动里——`schema.sql` 的每次修改都要同步 `schema.sqlite.sql` 并重跑 parity。

   只留 `'self'`，防 XSS 的那一条是完整的。HSTS 只在 TLS 连接上发（对 IP 本就不生效，等域名上线才起作用）。
5. 隐私与合规（一次做完，别拖）：页面底部放隐私说明；写明「只记录答题与掌握度，照片 30 天后删除」；
   备案信息在页脚展示（备案号 + 链接到工信部）。**⏳ 卡备案**

## 7. M3 · 题库建设（3 周，分批）

这是最重的一块，也是唯一一块**现在就能开工、且不受服务器影响**的——它可以在本机 SQLite 上跑通，
最后 `import_bank.py` 一次灌进生产库。

### 7.1 前置：把知识树补全（需要你拍课本目录）

现状：数学 8 单元 16 知识点是全的；**语文只有 1、2、7、8 四个单元，英语只有 1、2、8、9 四个单元**，
`verified` 全是 `false`。这不是「美化」，是硬伤：出题只取树里的知识点，树里没有的单元永远出不到题。

需要你做的只有一件事：**拍语文课本目录页、英语课本目录页**（单元名 + 每单元小标题即可），
我据此把 `server/content/curriculum/grade6-up.json` 补到 8 + 10 个单元，逐条标 `verified=true`、`source='ocr'`。

补完后知识点规模约 45–55 个（数学 16，语文约 14，英语约 17）。这个数是后面所有配额的乘数。

### 7.2 题量配额：为什么一个知识点是 12 题起

出题器有一条硬规则：**30 天内做过的题不再出**（`picker._candidates`）。一个孩子每天 5 题、约 50 个知识点，
平均每个知识点一周被抽到 1–3 次，一个月 4–12 次。所以：

| 档 | 数 | 用途 |
|---|---|---|
| **下限 `BANK_FLOOR`** | **12** | 3 个角度 × 2 个难度 × 2 题。刚好撑住 30 天不重复，是「这个知识点不缺题」的底线 |
| 一期目标 | 数学核心 24（分数乘除、圆、百分数、比）／其他 20／语文 20／英语 16 | 一期 ≈ 1000 题 |
| 二期目标 | 全部补到 24，数学核心 40 | 累计 ≈ 2000 题（E3 的「2000 题起步」） |

难度分布 1/2/3 = 4:4:2，角度 识记/理解/应用 = 3:4:3。分布写进 `docs/BANK.md`，由 `verify.py` 检查。

### 7.3 五道闸：什么叫「验算入库」

「AI 生题验算入库」不能只做数学。数学有 sympy 复算，语文英语没有——**没有复算标准的科目，必须换成
别的硬标准，否则会批量生产错答案，而错答案比没有题更糟**（孩子会把错的记牢）。五道闸依次过：

| 闸 | 查什么 | 怎么做 | 不过怎么办 |
|---|---|---|---|
| ① 结构 | 字段齐、题干 ≤120 字、选择题 4 个选项且互不相同、`qtype` 与答案形状一致 | `verify.py` 纯规则 | 拒 |
| ② 数学 | 答案对不对 | **生成器必须同时输出 `check_expr` 与 `check_value`**；服务端用 sympy 独立求值比对。**不解析自然语言**（`gen_seed_questions.py` 里 `EXPR_SAFE` 的道理一样） | 拒 |
| ③ 自洽 | 标注的答案是不是这题的真答案 | 把题干+选项**再喂一次模型**独立作答，与标注比对。成本约 ¥0.002/题，是性价比最高的一道 | 拒，或重生成 |
| ④ 去重 | 有没有和库里重复 | `(topic_id, template_key, param_hash)` 唯一键；另加题干归一化后 3-gram Jaccard > 0.8 拒 | 拒 |
| ⑤ 溯源 | 语文英语的答案凭什么 | 每条必须带 `source_ref`（课文篇目 / 单元 / 词表条目）；空的直接拒 | 拒 |

入库状态怎么落：

- 数学：②③ 都过 → `verify_status='sympy_ok'`，可立刻服务。
- 语文 / 英语：过 ①③④⑤ → 先落 `draft`（**不可服务**），抽检 20% 后由 `sample_audit.py` 批量置 `manual_ok`。
  抽检不合格率 > 5% 的批次**整批重跑**，不是逐题挑。

### 7.4 分批执行表（WorkBuddy 任务）

一批 = 一个单元，产出 `server/content/bank/grade6-up/<subject>/<unit>.jsonl`，跑 `verify.py`，通过率
< 85% 的批次重生成。26 批：

| 科目 | 批数 | 每批知识点 | 每批题数 | 累计 |
|---|---|---|---|---|
| 数学 | 8 | 1–3 | 36–48 | ~350 |
| 语文 | 8 | 2 | 40 | ~320 |
| 英语 | 10 | 2 | 32 | ~330 |

每批的提示词模板固定三样东西：本单元知识点清单 + 3 个已通过的好例题 + 禁项清单（不出现图、不出现听力、
不超过 120 字、答案必须唯一）。**模板进 git**（`server/content/bank/prompts/`），改了模板要重新记批次台账。

### 7.5 验收

- 26 批全部入 `docs/BANK.md` 的批次台账（批号、题数、通过率、抽检合格率）。
- `SELECT topic_id, COUNT(*) ... GROUP BY topic_id HAVING COUNT(*) < 12` 在 `verify_status IN
  ('sympy_ok','manual_ok')` 上返回空。
- 抽检工具能列出「随机 N 题 + 答案 + 溯源」，人工过一遍的时间控制在 1 小时内。
- 出题侧：随机 200 组 `pick_group`，不该出现「某知识点凑不出题降为 4 题」的日志。

## 8. M4 · 增量生题（1 周）

### 8.1 要改一处被刻意锁死的东西

`gen_task.route` 现在是 `ENUM('template')`，旁边写着「一条路，故意的，第二个值进来就是第二条产线」。
现在要开第二条产线了——**这是一次需要留痕的决策**，不是顺手加个枚举值：改 `route` 加 `'ai'`，
在 `docs/WRONGBOOK.md §8` 记一条 D 编号，两份 DDL 同步改，parity 重跑。

### 8.2 触发规则

每晚 **03:00（北京时间）** 扫描一次。这个时间是有意的：DeepSeek 峰时是工作日 UTC 01–04 与 06–10
（北京时间 09–12、14–18），凌晨跑正好是**半价**。

| 触发条件 | 排队 |
|---|---|
| `servable(topic) < BANK_FLOOR(12)` | 补到 12，正常优先级 |
| 该设备薄弱（`score ≥ 12`）且 `servable(topic) < target_qty(level)` | 补到 5/7/10，高优先级 |
| 昨日出现「组内不足 5 题」日志 | 相关知识点插队 |

每日预算：≤ 40 题（≈ ¥0.2）、≤ ¥5。超了第二天再补，**永远不为了补题超预算**。

### 8.3 与 M3 共用同一条管道

生成 → 五道闸 → 入库，一行代码不重复写。差别只有三处：题量小、要写 `gen_task` 的 `done_count`、
失败 3 次置 `failed` 并进每日通知。

### 8.4 验收

连续 7 天不开人工干预：每天 03:00 有 `gen_task` 记录、`done_count` 等于预期、白天没有缺题告警、
`failed` 为 0（或失败原因清楚）。第 8 天抽查 10 道自动补的题，人工判定全对。

## 9. M5 · 拍照 OCR（1 周）

### 9.1 落点

现有五个接口全部是设计好的空壳：`POST /v1/h5/paper/{id}/shot`、`/recognize`、`GET /draft`、
`POST /confirm`、`POST /abandon`。表也齐了（`paper.ocr_status`、`shot_count`、`purge_at`）。
缺的是一张 `paper_shot`（对象键、页码、sha256、宽高）——`paper.shot_count` 记不了「哪几张、存哪」。

### 9.2 链路

```
手机拍照 → 直传 OSS（私有桶，STS 临时凭证，图不过应用服务器）
        → qwen-vl-ocr 提文本 → qwen3-vl 切题（一次调用，要求输出 JSON：题号/题干/选项/手写答案）
        → 草稿落库（confidence 高/低）
        → 家长逐题确认（改知识点 / 改错几道 / 丢弃）
        → 复用 h5.add_paper 的掌握度路径，逐条 insert wrong_item 再 record_paper_wrong（20/8/8）
```

三个细节：

- **识别出来的题不进公共题库**，只进这个孩子的错题本（`wrong_item.source='paper'`）。版权和质量都不该
  让它污染共享题库。
- **照片 30 天删除**（`purge_at` 已经这么写了，D4），OSS 桶配生命周期规则兜底 + 一个每日清理任务把
  `purged_at` 补上。页面必须写明这一点。
- **失败要能退化**：识别不出来就回到「手选知识点 + 错几道」（P2 已经有的路径），不要让家长卡在一张
  糊了的照片上。

### 9.3 成本与验收

一页卷子约 6k token，`qwen-vl-ocr` 内地 ¥0.3/百万输入 → **约 ¥0.002 一张**，可以忽略。
验收：三张不同光线/角度的真实卷子，逐题确认后，错题清单里出现对应条目、掌握度加分正确、
下一组出现该知识点的题。

## 10. 排序与关键路径

```
        ┌── M3 目录核对（你，今天）── M3 分批生题（3 周）─────────── M4 增量（1 周）
M0 ─────┤
        ├── M1 电视端（3 天）── 观察 3 天
        └── M2 H5 公网（3 天）────────────────────────────── M5 OCR（1 周）

- **关键路径是 M3**，不是部署。部署 4 + 3 + 3 天能完，题库要 3 周，而且它第一步卡在「目录照片」。
  所以今天就要把照片要过来，而不是等 M0 做完。
- **M0 必须在 M1/M2 之前**，因为设备鉴权要跟着同一次 APK 发布走——分开做就要出两次包、装两次机。
- **M4 依赖 M3 的校验管道**，M5 依赖 M2 的上传页面。两者都不依赖对方，可以并行。

时间表（以今天 2026-11-16 为第 0 天）：

| 周 | 事 |
|---|---|

| 11/21–11/25 | M1（含 3 天观察）+ M3 第一批 |

期末大约在 1 月上中旬（假设），**一期题库要在 12 月中之前可用**，否则复习阶段没有题可巩固——
这也是把 M3 提前、把 M4/M5 推后的原因。
