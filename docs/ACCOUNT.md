# 账号与登录：设计说明

> **状态**：2026-11-14 定案并开始实现。上一版是「cookie 就是唯一凭证、没有账号」（D5 未定），
> 一个浏览器只能管一台电视，换一台就得重新取码。本文件替换那一节。
>
> **与其它文档的关系**：`docs/PARENTAL.md` 仍管电视端和家长模块的行为；`docs/QUIZ.md` 管做题与票。
> 本文只加一层：**谁在操作**。

---

## 1. 一句话

手机上加一个邮箱 + 密码的账号，**凭证从「这台手机绑过这台电视」变成「这个人是谁」**；
一台电视可以绑多个账号（爸爸 + 妈妈），一个账号可以绑多台电视。

## 2. 为什么现在改

| 现状 | 后果 |
|---|---|
| cookie 里装的是某一台电视的 token | 同一浏览器配第二台电视，第一台就管不了（cookie 被覆盖） |
| 没有账号 | 换手机 = 在电视上重新取码；手机清了缓存 = 同上；爸爸和妈妈只能共用一台手机 |
| 没有「我是谁」 | 审计表只能记「h5」，记不了「谁改的」；多台电视没法在一个页面里切 |

## 3. 决定

**A1 邮箱 + 密码，不做邮箱验证。** 没有邮件网关，验证信发不出去。诚实的结论是：
**邮箱是登录名，不是所有权证明。** 由此派生的三条，必须一起接受：

1. **「忘记密码」只能靠自设的安全问题**（发不了重置信）。注册对「邮箱 + 两次密码」是必填，
   问题是**选填**；填了问题就必须填答案（反之亦然，只有答案没有问题的组合会被拒）。
   忘记密码时走 `邮箱 → 看问题 → 答案 → 两次新密码`。答案按口令一样用 scrypt 存，不存明文；
   连错 5 次锁 15 分钟（落库）。这条是 2026-11-15 补的，取代了原先「不做找回」的写法。
   它换来的是可用性，代价是安全性降一档——见 §11。
   选填的原因：注册那一刻家长往往想不出「只有自己知道答案」的问题，强制填只会让人乱写或干脆放弃；
   不填的账号之后可以在设置页补（§11.3），补上之前它确实找不回，界面上如实这么写。
2. 任何人可以拿别人的邮箱注册（先用先得）。因为邮箱不用于任何通知，冒用的后果只落在冒用者自己身上。
3. 也不发任何营销/通知邮件。以后接了网关，再加 `email_verified_at` 一列就能补验证，不用改表结构。

**A2 一个账号可以绑多台电视，一台电视可以绑多个账号。** 这直接解掉 D6（多家长）和「两个浏览器」两个问题。
绑定关系单独一张表 `account_device`，不再往 `device` 上写 token。

**A3 session cookie 仍是搬运凭证的方式，但它的含义变了。** cookie 里装的是**账号会话**（30 天，每次用顺延，最长 90 天），
不再是某台电视的 token。电视那侧没有任何变化：它只认 `device_id`，不知道账号存在。

**A4 绑定仍然要电视上的六位码。** 码证明「你人在这台电视跟前」，账号证明「你是谁」。
两者缺一不可：光有账号不能凭空认领一台电视，光有码也只能加到**自己已登录的账号**上。

**A5 旧手机不抛弃。** 已配对的手机升级后第一次打开，服务端发现 cookie 里是**设备 token 而不是会话**，
返回 `legacy: true`，页面引导「设一个邮箱密码，把这台手机升级成账号」——建账号 + 绑定当前设备一步完成，
原来的绑定关系不丢，电视上不用重新取码。

## 4. 数据

```sql
account(id ULID PK, email, email_key UNIQUE, password_hash, fail_count, locked_until,
        created_at, last_login_at, disabled_at)
account_session(token_hash PK, account_id, created_at, last_seen_at, expires_at)
account_device(account_id, device_id, bound_at, PRIMARY KEY(account_id, device_id))
```

- `email` 存用户输入的样子，`email_key` 是 `strip().lower()`，唯一索引建在它上面（`A@x.com` 和 `a@x.com` 是同一个人）。
- `password_hash` 是自描述字符串：`scrypt$N$r$p$<salt b64>$<hash b64>`。参数变了也能验旧口令。
- `device.token_hash` 保留但**不再写入**，只用于 A5 的迁移判断；迁移完成即清空。
- `device.bound_at` 变成「至少还有一个账号绑着」的派生值：最后一个账号解绑时清零，电视那边的心跳才能把设置页写回「未连接」。

## 5. 口令怎么存

`hashlib.scrypt`，`N=2^15, r=8, p=3`（OWASP 给的第二档，一次约 270 ms / 32 MiB）。
不引第三方库：Argon2 在标准库里没有，scrypt 有；这两档的防护强度 OWASP 认为是同一级。

- 每个口令一个 16 字节随机盐；比较用 `hmac.compare_digest`。
- 口令长度 8–128 字节；拒绝与邮箱前缀相同、拒绝一张 20 条的常见口令表（`12345678`、`password`…）。
- 参数写在哈希串里，将来调高只影响新口令，旧口令验证时按串里的参数走。

## 6. 防刷（没有验证码、没有邮件网关的前提下）

四层，全部无需外部服务：

| 层 | 规则 | 为什么够 |
|---|---|---|
| 单 IP 限速 | 注册 5/小时、20/天；登录 20/15 分钟 | 家用宽带 NAT 后面就一台路由器，按 IP 够了 |
| 全站闸门 | 注册 60/小时，超过返回 429 | 防分布式刷号把库刷满；正常家庭永远碰不到 |
| 签名挑战 | `GET /v1/auth/challenge` 发一个 HMAC 签名的 `issued_at`，注册时必须带回；**年龄 < 1.5 秒或已用过**就拒 | 手写脚本要模拟「人打开表单、读、填、提交」的节奏，成本高于收益；不用验证码也不用手搓前端 |
| 蜜罐 + 口令强度 | 表单里有一个屏幕外、`tabindex="-1"`、`autocomplete="off"` 的 `website` 字段，非空即拒；口令长度和常见表 | 挡住最便宜的那批扫描器 |

登录另有一条：**同一账号连续 8 次失败锁 15 分钟**，计数写库（`account.fail_count` / `locked_until`），
重启不清零；单 IP 的计数在内存里，重启清零——它是闸门，不是账本。

明确**不做**的：图形验证码（要引入依赖、无障碍差、对脚本几乎无效）、工作量证明（前端没有构建步骤，
纯 JS 循环要几秒，体验代价大于收益）。以后被刷了再说，先上表里这四层。

## 7. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/auth/challenge` | 发注册挑战（`{challenge, issued_at}`） |
| POST | `/v1/auth/register` | `{email, password, question?, answer?, challenge, website}` → 建号并登录；问题与答案要么都给、要么都不给 |
| POST | `/v1/auth/login` | `{email, password}` → 会话 cookie |
| POST | `/v1/auth/logout` | 清 cookie，删这一条会话 |
| GET | `/v1/auth/me` | `{account, devices[]}`；未登录 401；旧 cookie 返回 `{legacy: true, device}` |
| POST | `/v1/auth/claim` | 旧 cookie + 新邮箱密码（问题答案同上，可选）→ 建号、绑定当前设备、清旧 token |
| POST | `/v1/auth/password` | **需要会话**：`{old_password, password}` → 改密并**吊销该账号全部会话** |
| POST | `/v1/auth/question` | `{email}` → `{question}`；无此账号 404，没设问题 409 |
| POST | `/v1/auth/question/set` | **需要会话**：`{question, answer}` 设或换问题 |
| POST | `/v1/auth/recover` | `{email, answer, password}` → 重设密码并吊销全部会话，**不发会话** |
| POST | `/v1/h5/pair` | **需要会话**：六位码 → 把该设备加进当前账号 |
| POST | `/v1/h5/unpair` | 只删「我」和这台设备的绑定；我是最后一个则清 `bound_at` |

`/v1/h5/*` 的其余路由不变，但取设备的方式从「cookie 里的 token 反查」变成
「会话 → 账号 → 设备必须在 `account_device` 里」。越权一律 403/404，不泄露设备是否存在。

## 8. 电视那侧要改的三处

1. `pair/renew` 不再因为「已绑定」拒绝——第二个家长要能加入。真正的门是电视上的家长密码（取码入口本来就在它后面）。
2. 「换一台手机」按钮改为**不重建设备**：只重新要一个码，`device_id` 保留，今日计数和历史都还在。
   （上一版为了绕开「已绑定不再发码」才重建设备，账号上线后那个理由消失了。）
3. 心跳里的 `bound` 改看「`account_device` 里还有没有这个设备」，因为 `token_hash` 不再写入。

## 9. 验收

1. 新电视 → 取码 → 手机注册 → 码填进手机 → 电视三秒内变「已连接」。
2. 同一账号配第二台电视 → 手机两个都看得到，切换后能分别改设置。
3. 第二个家长注册 → 电视上再取一次码 → 两台手机都能管同一台电视；**一台解绑，另一台不受影响**；都解绑后电视回到「未连接」。
4. 已配对的旧手机升级 → 打开就是「升级成账号」，设完邮箱密码仍停在原来那台电视，`device_id` 不变。
5. 退出登录 → 手机只剩登录页；电视不受影响（它不知道账号）。
6. 注册 6 次（同 IP）→ 第 6 次 429；登录连错 8 次 → 账号锁 15 分钟，换 IP 也一样（锁在账号上）。
7. 挑战年龄 < 1.5 秒 / 同一个挑战用两次 → 400。
8. 拿别人的 `device_id` 调 `/v1/h5/summary`（会话有效但不属于该设备）→ 403。
9. 注册时两次密码不一致 → 前端就拦住（不发请求）；口令只有数字 → 规则不亮且提交被拒。
10. 注册不填问题也能成功；只填答案不填问题 → 400 `answer-orphan`；有问题但答案空白 → 400 `answer-short`；没问题的账号查问题 → 409 `no-question`。
11. 登录态改密：旧密码错 → 403；两次新密码不一致 → 前端拦住；改成功 → 该账号**所有**手机会话失效，回到登录页。
12. 找回：输邮箱 → 问题原样显示；答错 → 403 且什么都不改；连错 5 次 → 锁 15 分钟；答对 → 重设成功并吊销全部会话，**不发会话**。
13. 老账号（`recovery_question` 为空）在设置页补设问题后，可立刻用新答案找回。

## 10. 还没做

- 邮箱验证（要网关）。
- 账号注销 / 导出。
- 邀请码、家庭组命名、角色（都是 A2 之上的锦上添花）。
- 第三方登录（微信 / Google）。

## 11. 口令规则、改密、找回（2026-11-15 增补）

### 11.1 口令规则

服务端 `password_problem()` 是唯一裁判，前端那份清单只是它的影子：

| 规则 | 错误码 | 为什么 |
|---|---|---|
| ≥ 8 位 | `password-short` | 下限 |
| 不能只有数字 | `password-weak` | 手机上「12345678」是家长手最快的一条 |
| 不在常见口令表里 | `password-common` | 字典第一批 |
| 不等于邮箱前半段 | `password-is-email` | 一条就能猜中 |
| 改密时不能与旧口令相同 | `password-same` | 等于没改 |

前端把同样五条做成实时清单（`data-rule` + `.rules`），逐条变绿。**清单必须和服务端一一对应**，
否则会出现「全绿但被拒」——那是比不给提示更糟的体验。

两次输入只在浏览器里比对（`checkLocally`），不作为接口参数：服务端收到的永远是已经确认过的那一个。

### 11.2 提示问题是弱凭证，按弱凭证处理

它由家长自己写，往往熟人就能猜到，而它能直接重置密码。所以：

| 措施 | 取值 |
|---|---|
| 答案存储 | `hashlib.scrypt`，与口令同一套参数，**不存明文、不存大小写** |
| 答案比对 | 去首尾空白、折叠中间空白、`casefold`；`  Red  APPLE ` 等于 `red apple` |
| 每账号连错 | 5 次 → 锁 15 分钟，`recover_fail_count` / `recover_locked_until` 落库 |
| 每来源 | 查问题 20 次/15 分钟、提交答案 20 次/15 分钟，两个额度分开 |
| 邮箱不存在时 | 回 `no-account`，但先做一次等价的 scrypt 运算，响应时间不泄露账号是否存在 |
| 答对但口令太弱 | **不计数**，同一个答案可以再试一次——不能因为选了个弱口令就把唯一一次好答案烧掉 |

顺带说明为什么不用恢复码：恢复码是一次性凭证，家长抄在纸上会丢，而且它和「换个邮箱重注册」
一样，出问题时没有任何人工兜底。问题答案至少是家长自己记得住的。

### 11.3 改密与找回都吊销全部会话

`change_password()` 和 `recover()` 都在同一个事务里删掉 `account_session` 里该账号的所有行。
理由一致：这两个操作的语义都是「把账号收回来」，留着别的设备上的 cookie 等于没收回来。
代价是当前这台手机也要重新登录——这正好是「新口令确实能打出来」的验收动作，不是纯粹的麻烦。

### 11.4 五个新用例之外，还补了一条迁移路径

`recovery_question` 是后加的列，**已有账号的值是 NULL**。为此加了 `POST /v1/auth/question/set`
（设置页「找回问题」）：老账号补上，设错的也能改。没有它就等于给老账号判了「永远找不回」。
注册时跳过问题的账号走的是同一个入口——两条路都通向「这个账号现在能找回了」。
