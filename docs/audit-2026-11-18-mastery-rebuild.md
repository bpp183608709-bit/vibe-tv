# 审查：六年级上册掌握度重构的落地情况

> 审查对象：`# 任务：重构小学六年级上册语数英知识掌握评测系统` 这份设计稿（下称「设计稿」）
> 与当前仓库实现（`b7c158e`）的逐条比对。
> 审查时间：2026-11-18。基线：`acceptance` 248/248、`check_content` ok、`check_schema_parity` 26 表 237 列。
>
> **结论先说**：设计稿的目标（三层节点、滚动窗口掌握度、两级报告）都实现了，可运行、可验收。
> 但**交付物的形态**与设计稿要求有明显偏离：设计稿定义了一组扁平 JSON 结构，
> 我们落地成了「树形数据 + 数据库表 + 服务端端点」，靠一层翻译函数去满足 schema。
> 另外有 1 处实质性数据遗漏和 4 处结构性不符，见下。

---

## 0. 分级口径

| 级别 | 含义 |
|---|---|
| **P0 缺陷** | 违反设计稿硬性要求，且当前没有任何检查能挡住 |
| **P1 结构偏离** | 功能在，但交付物形态不是设计稿要求的那一种 |
| **P2 形式/文档** | 字段、冗余列、文档表述层面的不一致 |
| **P3 已批准的偏离** | 用户 D1–D6 明确决策过的，记录在案但不算缺陷 |

---

## 1. P0：一个微知识点被静默丢弃

**事实**：设计稿 §3.1 规则 1 要求「拉取全部 38 个微知识点」。实际只有 **37 个**被引用。

```
未引用：mt_g6u_036「分数四则混合运算」
        centrality 0.8（38 个里最高一档）
        standards: pep-math-2022:6上.总复习.1
        并且是 mt_g6u_034「节约用水的数据统计」的先修项
```

**后果**：

- 六上"分数四则混合运算"这个能力没有任何诊断节点承载；
- `mt_g6u_034 → mt_g6u_036` 这条先修边随之一并失效（一端没有节点，边就落不了地）；
- 报告里永远不会出现这一类错误，家长看不到，验收也测不到。

**原因**：归并脚本按「教材章节」分组，`mt_g6u_036` 的 `standards` 是「总复习」、`domain` 是「数与代数」，
不落在任何一章里，被归并逻辑直接跳过。而 `check_content.py` 的校验是**单向的**——
它检查「节点引用的 `source_id` 是否存在」，不检查「快照里的 38 个是否都被引用」。
所以漏一个不报错，漏十个也不报错。

## 2. P1：四处交付物形态偏离

### 2.1 节点数据不是 §4.1 的形状

设计稿 §4.1 定义了 13 个字段的扁平节点对象。实际 `server/content/curriculum/grade6-up.json`
用的是另一套：

| 设计稿字段 | 实际 | 差异 |
|---|---|---|
| `node_id` | `code` | 名字不同（值格式 `math-6up-d01` 是符合的） |
| `name` | `name_zh` | 名字不同 |
| `node_type` | 无 | **缺**，靠「在 units 里还是在 topics 里」隐含 |
| `parent_id` | 无 | **缺**，靠嵌套隐含 |
| `chapter_name` | 无 | **缺**，靠父级 `unit.name_zh` |
| `prerequisite_node_ids` | `prereq` | 名字不同 |
| `description` | `summary_zh` | 名字不同 |
| `status` | 无 | **缺** |
| `micro_nodes` | 对象数组 `{source_id,name,evidence,assessment_prompt}` | **结构不同**（设计稿要求 `["string"]`） |

**关键点**：`server/content/schema/node.schema.json` 是照设计稿写的（含 `node_type`/`parent_id`/`status`），
但数据文件根本不长这样。校验能通过，是因为 `check_content.flat_nodes()` 在中间做了一次**翻译**：

```python
# server/tools/check_content.py:45-84
"node_id": topic["code"],
"node_type": "diagnostic",
"parent_id": unit_id,
"micro_nodes": [m["name"] for m in topic["micro_nodes"]],   # 对象 -> 字符串
```

所以「schema 通过了」这件事，证明的是翻译函数正确，不是数据符合设计稿。

**附带问题**：同一函数里，聚合节点的 `knowledge_type` 是**硬编码编出来的**——
数学一律 `procedural`、英语一律 `reading`、语文一律 `阅读理解`。设计稿没有要求聚合节点有
`knowledge_type`，这个值纯粹是为了让 schema 的非空约束过关。

### 2.2 没有 `scripts/evaluate.py`

设计稿 §7.4 要求一个独立脚本：「接收 `answer_records` 和节点/题目数据，输出符合第六节结构的报告 JSON」。

实际提供的是 `server/app/report.py`（纯函数 `build(groups, period)`）+ `h5.report_by_node()`（取数）
+ `GET /v1/h5/mastery/report`（HTTP）。**功能等价，形态不同**，而且不能离线跑——
它读的是 MySQL 里的实时数据，不接文件。

### 2.3 报告列出了全部已测节点，而设计稿要求只列薄弱项

设计稿 §6.3：「报告按聚合节点分组展示，组内按诊断节点列出**薄弱项**」。

实际 `report.build` 的过滤条件只有 `sample >= 3`（是否测过），然后**所有**已测节点都进 `diagnostics`，
包括「2-熟练」和「3-拓展」。`_selfcheck` 里就有一条断言在验证这一点：

```python
# server/app/report.py:120
assert chapter["diagnostics"][1]["mastery_level"] == "3-拓展"   # 非薄弱节点也在列表里
```

只有 `weak_diagnostic_count` 是严格按 `level <= 1` 计的。这是「章节全貌视图」而不是「薄弱清单」，
两种都合理，但和设计稿写的不一样。

### 2.4 §4.4 的 `weakness` 结构没有落地

设计稿定义了独立的薄弱项对象（`weakness_id` / `parent_aggregate_node_id` / `parent_aggregate_name` /
`evidence_question_ids` …）。实际没有这个实体，薄弱项 = `topic_mastery` 里 `level <= 1 且 sample >= 3` 的行，
由 `h5.weak_list()` 现查现拼，没有 ID，也不落库。

## 3. P2：形式与文档层面的不一致

| # | 问题 | 位置 | 说明 |
|---|---|---|---|
| 3.1 | `question.unit_id` 是 `NOT NULL`，39/39 都有值 | `schema.sql` question 表 | 设计稿 §4.1 要求「aggregate 节点不绑定题目」。物理上题目确实挂在 unit 上，而且 `picker._candidates` 用 `JOIN unit u ON u.id = q.unit_id` 取 `u.ordinal` 决定「当前单元 / 已学 / 未学」——**聚合节点在影响出题**。判档没用到它，但「不绑题」这条是形式上的违反 |
| 3.2 | `answer_record` 缺 `diagnostic_node_id` 与 `ability_tag` | `quiz_answer` 表 | 只有 `question_id`，两者要靠 join 反查。§4.3 要求冗余存储 |
| 3.3 | `mastery_snapshot` 没有 `ability_breakdown` | `topic_mastery` | §4.3 要求按能力线下钻的数组；实际只在生成报告时现算一句 `ability_breakdown_note`，不持久化 |
| 3.4 | `data_sources.md` 缺逐节点映射 | `docs/data_sources.md` | §7.5 要求「英语：每个诊断节点对应的单元和语法点来源」「语文：每个诊断节点对应的能力方向和覆盖课文」。文档只有汇总表，逐节点信息在 `grade6-up.json` 里，没写进文档 |
| 3.5 | `data_sources.md` 关于数学广角的表述与数据不符 | 同上 §2 | 文档写「032/033 属于数学广角、024/034 属于综合与实践，都不是独立章节，**已并入相应单元**」。实际数据里 U8 就叫「数学广角——数与形」、U9 就叫「综合与实践」，是**独立单元**，各挂 1 和 2 个节点 |
| 3.6 | 题目 `options` 是 `[{label,text}]`，设计稿要求 `["string"]` | 三个题库文件 | 更实用（TV 需要 label），但结构不同。数学多出的 `accepted`（多答案）也是设计稿没有的扩展 |
| 3.7 | 每道题没有 `subject` 字段 | 三个题库文件 | `subject` 在文件顶层。§4.2 要求每题带 |
| 3.8 | 聚合节点没有稳定 ID | `grade6-up.json` | unit 只有 `ordinal`；报告里的 `aggregate_node_id` 是现拼的 `math-6up-u01`，库里不可寻址 |

## 4. P3：用户已批准的偏离（记录，不算缺陷）

| # | 偏离 | 决策 | 影响 |
|---|---|---|---|
| 4.1 | 交付物落 `server/content/` 与 `server/app/`，不建 `data/` + `schemas/` + `scripts/` | D1 | 复用既有导入管道，避免两套并行 |
| 4.2 | 掌握度全量换加权正确率，历史数据清空 | D2 / D5 | 已执行，旧数据有备份 |
| 4.3 | 语文按 8 个单元（设计稿只列 6 个） | D3 | 补上「艺术之美」「走近鲁迅」；设计稿 §1 说以提示词目录为准，此处被用户覆盖 |
| 4.4 | 英语按 2026 新版 10 单元 | D4 | 与设计稿一致 |
| 4.5 | 不做简答题，用「选择式简答」（选择题）替代 | D6 | 全库 32 选择 + 7 填空，无判断题、无简答 |

其中 4.3 值得单独说一句：设计稿 §3.3 只列了第一到第六单元，但统编版六上实际是 8 个单元。
按 6 个建树，学期后三分之一（第七、八单元）会没有节点可挂。这一条是**照设计稿做反而错**的情形，
用户 D3 的决策是对的，但意味着这一处**没有严格按提示词落地**——这是有意的。

## 5. 原因归因

四类，按可修复性排序：

**A. 归并时的静默遗漏（P0）**
人工把 38 个微观点映射到 24 个节点，映射表写在一次性脚本里（未入库）。
`mt_g6u_036` 因为 standards 落在「总复习」、不对应任何一章而被跳过。
根本原因是**校验器只做了「引用→存在」的单向检查**，没有做「快照→覆盖」的反向检查。
这是唯一会在无人察觉的情况下丢失教学内容的问题。

**B. 为复用既有管道而做的结构妥协（P1 大部分）**
既有系统是「树形 JSON + 中文键 + 导入 MySQL」，设计稿是「扁平 JSON + 英文键 + 离线脚本」。
D1 选择复用既有管道后，两套结构只能二选一：要么改数据文件（等于重写导入器和全部下游），
要么加一层翻译（`flat_nodes`）。选了后者，于是 schema 成了「翻译产物的约束」，
而不是「数据文件的约束」。`evaluate.py` 缺失同理——报告变成了一个服务端端点。

**C. 实现时对需求的语义理解偏差（P1 2.3）**
把「报告」理解成「章节全貌」而不是「薄弱清单」，因为家长页的实际需要是全貌。
这是**产品判断覆盖了文字要求**，方向未必错，但没有在设计稿层面留下记录。

**D. 旧 schema 未清理 + 文档滞后（P2）**
`question.unit_id` 是引入诊断节点之前就有的列，出题索引依赖它取单元序号，迁移时保留了下来。
`mastery_event`、`answer_record` 的字段缺口同理——新模型的字段是**加**上去的，旧字段没有一并收敛。
`data_sources.md` 是最后写的，写的时候按「归并规则」组织，没有回头核对 §7.5 的逐项要求，
于是漏了逐节点映射，数学广角的描述也停在了归并脚本的中间态。

## 6. 如果要修，顺序建议

| 顺序 | 事项 | 代价 |
|---|---|---|
| 1 | 补 `mt_g6u_036`：加一个节点，或并入「分数除法」/「综合与实践」现有节点；同时在 `check_content` 加反向覆盖检查（38 个必须全被引用） | 小，1 个节点 + 1 条断言 |
| 2 | `data_sources.md` 补逐节点映射表；修正数学广角那句 | 小，纯文档 |
| 3 | 报告增加一个 `scope` 参数：`weak`（只列薄弱，符合设计稿）/ `all`（章节全貌，当前行为） | 小，一个过滤条件 |
| 4 | 清掉 `question.unit_id`，改用 `JOIN topic t ON t.id = q.topic_id` 取 `t.unit_id` 再取 ordinal | 中，要动 `picker._candidates` 与索引，需重跑验收 |
| 5 | 节点数据改成 §4.1 扁平格式 | 大，等于重写导入器与 `flat_nodes`，收益主要是"让 schema 名副其实" |

前 3 项加起来不到半天，第 4 项要看是否愿意动出题主路径。

---

## 7. 一句话总结

功能层面完成度高（248 条验收全绿、三科题库与节点树齐备、掌握度算法与设计稿逐条吻合）；
**形式层面有一层"翻译"**——设计稿要的文件形态、离线脚本、扁平结构没有交付，
用数据库和服务端端点代偿了同一组功能。
真正的缺陷只有 1 个（漏了 `mt_g6u_036`），其余是形态与文档层面的欠账。
