## 1. 一句话

每天的额度从一个"配给数"变成"基础额度 + 自己挣的"，挣的方式只有一种：**在电视上做一组题，由服务端判分并签一张票，电视离线验票，把票换成当天的分钟数。**

判分不上电视，是因为额度写在本地的数字里，而票来自一个不可信的客户端——两者之间唯一的防线是签名。

## 2. 额度模型

当日可看总量 = **基础额度 + 密码加时 + 做题所得**。三类来源，一条解除：

| 来源 | 谁给 | 每次多少 | 有上限吗 |
|---|---|---|---|
| 基础额度 | 设置页，每天一个数 | 60 分钟（G1 已定） | 无 |
| 密码加时 | 锁屏页「快速延长」→ 家长密码 | 30 分钟 / 1 小时 | **不限次数**（C8，户主明确） |
| 做题所得 | 服务端签票，本地兑换 | 通过即 30 分钟（B2/B3） | **3 次 / 90 分钟**（B4） |
| 今日不再限制 | 密码后的第二层（C10） | — | 每天一次，只管每日上限 |

**通过线是 80%**（B2，2026-11-11 修正）：一组 5 题，答对 4 题即通过，通过就给满 30 分钟。**没有半份**——早先草案里的「错 1 题给一半」已作废，一个数字比两个数字好解释，也好守。3 次 × 30 分钟 = 90 分钟，两个上限天然对齐。

> 题组少于 5 题时（C2 允许因题量大而减题），80% 按向上取整算：4 题要全对，3 题也要全对。所以**默认永远是 5 题**，减题只在该知识点凑不出 5 题时发生，并在日志里记一笔。

**60 + 90 = 150**，正好是 A5 说的周末实际观看量（G1 已定）：基础额度天天相同，周末那 90 分钟靠做题挣。

**账只有一个，上限分两种。** 做题所得的分钟数和密码加时的分钟数都进 `dailyExtraMs`，跨天清零；「3 次 / 90 分钟」只数做题那一条，密码加时不动它，反过来也一样——这正是 A6 说的"单独计额度"。

A6 的场景因此成立：家长先看完基础额度 → 输密码加 → 再看 → 再输密码加 → 家长走了，孩子没有密码 → 锁屏上只剩做题入口。**不需要切换角色**，因为判断"谁在看"从来就不可能，能判断的只有"现在还能不能加"。

**为什么不做成按序消耗的三个桶**：谁在看判不出来，按序消耗只是账面区分，实际消耗无法归属。分开记的是计数，不是顺序。

**`dailyMinutes = 0`（不限）时做题机制整体关闭**：没有锁屏可挂，入口不出现，设置页显示"当前不限时，做题换时长不生效"。这是对 HANDOFF 冲突二的答复。

## 3. 状态机与页面

`WatchTimer` 的**三态不变**（`Normal` / `Interval` / `DailyLimit`）。「赚取中」不是第四个状态，是 `DailyLimit` 之上的一层页面：

```
DailyLimit 锁屏页
  ├─ 去做题 ──────────► 做题页（QuizActivity），ParentalClock 不累加
  │                        ├─ 交卷通过 → 兑换 → Parental.extendDaily(30min) → 立刻解锁
  │                        ├─ 交卷不通过 → 回锁屏页，显示冷却倒计时
  │                        └─ 3 分钟无操作 / 整组 10 分钟超时 → 退出（C17/C4）
  └─ 快速延长 ────────► 密码页 → 30 分钟 / 1 小时 / 今日不再限制（C9/C10）
```

两条必须写进代码的约束：

1. **做题页不计时。** `ParentalClock` 每秒 tick 时看 `QuizSession.active`，为真就只 `idle()` 不 `tick(watching=true)`。否则孩子在做题页待着就在烧额度，等于罚他做题。
2. **guard 不得在做题页上再抬锁。** `HomeGuardService.needsPin` 对做题 Activity 放行一条。锁屏页仍然是 `DailyLimit`，做题页关掉就回到它，不需要新状态。

间隔锁屏页（`Interval`）也放做题入口（B8-C）。**但两者同时出现的处理按 B8 的答复**：做题过程时间与冷却时间都计入间隔时长的消耗；通过后若间隔已耗尽则直接解锁，未耗尽则回间隔锁屏继续倒计时。

## 4. 链路

```
① TV: POST /v1/quiz/next            → 服务端按 curriculum_progress 选题组（≥2 学科，5 题）
② TV: 显示题（答案随题下发，见 G2）→ 本地预判：每题即时给正误，仅用于界面
③ TV: POST /v1/quiz/{id}/grade      → 服务端判分（唯一权威）
                                       通过 → 写 daily_state、插 ticket 行、返回签名凭证
④ TV: 验签 → 查本地已花 jti → 查当日上限 → Parental.extendDaily(ms) → 立刻解锁
```

③ 到 ④ 之间断网，③ 的响应没拿到就等于没通过：本地不判、不加、不发。④ 之后断网不受影响，票已经在手里。

**预取**（D2）：本地常备 3 组题，API 挂掉时孩子仍能答题、仍能交卷——但只要 ③ 不通就没有额度。预取组的存在是为了不让孩子对着"网络错误"发呆，不是为了离线加时长。

## 5. 知识点树

```
学科 subject → 册 textbook(版本+年级+学期) → 单元 unit → 知识点 topic → 考察角度（题目上的字段）
```

- **册**是树的根，因为 A2 的教材版本一旦错，整科作废。`textbook` 唯一键 = (学科, 出版社, 年级, 学期)。
- **单元**带 `week_start`，C3-B 的校历自动推进用它算"现在该学到第几单元"，家长只改 `curriculum_progress`，不改校历。
- **知识点**是错题统计、相似题生成、进度匹配三者共同的主键。E4：一题一个主知识点，约 10% 挂第二个。
- **考察角度**（识记 / 理解 / 应用，E5）是**题目**的属性，不是知识点的属性——同一个知识点要能出三种角度的题。

本期实到：六年级上册，数学（人教）、语文（人教）、英语（湘少版）。科学（教科版）与道法**不入库**（G5 已定：这学期期中期末不考科学）。

> 2026-11-11 更正：语文由"部编"改为**人教**（户主看课本封面确认）。统编教材本就由人教社出版，"部编"是俗称，`publisher` 统一记 `pep`，与数学同值。这处不是笔误——录题时按 `publisher='pep'` 取册，若沿用旧称 `bubian` 会取不到语文册。

表结构见 `server/db/schema.sql`，字段注释在英文，理由在这里。

## 6. 题目与出题

| 约束 | 值 | 出处 |
|---|---|---|
| 题面长度 | ≤ 120 字（短篇阅读正文同此上限） | E9 / HANDOFF |
| 题型 | 只有 `choice`（4 选 1）与 `fill`（填数字或短词） | E8 |
| 不做 | 400 字以上阅读、几何作图、统计图读图、英语听力 | E9/E10 |
| 组内题数 | 5 题；仅在该知识点凑不出时降为 4 或 3，并记日志 | C2 |
| **通过线** | **正确数 ≥ ⌈0.8 × 题数⌉**（5 题 → 4 对；4 题、3 题 → 全对） | B2 |
| 通过所得 | 30 分钟，与 5 对还是 4 对无关 | B2/B3 |
| 入库门槛 | 数学必须 `sympy` 复算通过（`verify_status='sympy_ok'`） | E6 |
| 抽检 | 5%，数学优先（`tools/sample_audit.py`） | E7 |
| 规模 | 2000 题起步 | E3 |

**出题规则**（`POST /v1/quiz/next`）：

1. 取三科各自的当前单元（`curriculum_progress`，校历自动推进）；
2. 排除本机 30 天内做过的题（`quiz_answer` 上的索引就是去重表）；
3. 错题加权：`topic_signal.wrong_count` 高的知识点多出（C6）；
4. 至少 2 个学科、每科至少 1 题（C5）；默认 5 题，题库不足以凑 5 题时按 4→3 递减（C2）；
5. 连续失败 3 次后难度 -1，**界面不提示**（C7）；
6. 出题时把 `quiz_session.question_ids` 固化，交卷只能按这个顺序，防止重交时换题。
7. 错题训练段（`docs/WRONGBOOK.md`）**不向电视端暴露任何标记**：没有知识点名、没有「复习」字样、
   没有次数与进度，响应体也不多任何字段——与 C7「难度回退界面不提示」是同一条原则：
   调度策略对孩子不可见，孩子只从题目频次感知变化。
8. 五题的**来源配比**由 `server/app/mix.py` 定：当前单元 `c` 题、前 2–3 单元若干、错题训练段 `r` 题，
   `(c, r)` 一天一算存 `daily_state`。三条硬约束：**R 段先取**（否则会被每科轮一题挤掉）、
   **单知识点每日 ≤3 题**（按「进 R 段的次数」数，未提交的组也占名额）、
   **配额是目标不是墙**（当前单元没题可超 `c`，R 段没题可把题位还给课程段，五题总数不变）。
   M 全为 0 时退化为改造前的行为，`server/tools/acceptance.py` 里有一份冻结实现逐题比对。

## 7. 凭证

格式与实现：`server/app/ticket.py`（自检 `python -m server.app.ticket` 已通过）。

```
AQ1.<base64url(payload)>.<base64url(signature)>
payload = {v, alg, jti, did, day, ms, iat, exp}
```

签名覆盖 `AQ1.<payload>` 全部字节，包括前缀。

| 字段 | 用途 | 校验不通过时 |
|---|---|---|
| `alg` | `ES256`（唯一生产算法，G3 已定）/ `HS256`（仅本地开发） | `bad-alg` |
| `did` | 设备绑定，票只在这台电视上有效 | `wrong-device` |
| `day` | 签发当天，**与本地 `dayKey()` 相同** | `wrong-day` |
| `ms` | 只允许 1800000 一个值（通过即 30 分钟） | `bad-award` |
| `jti` | 一次性，本地记已花掉的 | `spent` |
| `exp` | 24 小时 | `expired` |

**`day` 在 `exp` 之前生效**：23:50 签的票到 00:10 已经没用，因为它要加的那个计数器在凌晨 4 点（C1，G4 已定：整机统一）已经归零了。不做这一条，隔夜攒票就成了漏洞。

**算法用 ES256**（G3 已定）。本地验签意味着密钥必须在 APK 里：HMAC 的密钥一旦打包，拆包即得，等于没有签名；ECDSA 只把**公钥**放进 APK，拆包拿不到能签票的东西。JCA 从 API 11 起就有 `SHA256withECDSA`，**不需要任何第三方库**。代价是 APK 里多一个公钥常量、服务端多一个 `cryptography` 依赖（`server/tools/genkey.py` 生成密钥对）。

**本地兑换的二次检查**（与服务的检查不重复，防的是恢复备份、复制文件、重放）：`ms` 在允许集合内、`did` 是自己、`day` 是今天、`jti` 没花过、当日做题次数与分钟数未超上限。这五条任何一条不过，票作废且不提示"为什么"。

| 攻击 | 挡住了吗 | 靠什么 |
|---|---|---|

## 11. 派生决策：G1–G7（已定 2026-11-11）

| 编号 | 结论 | 落点 |
|---|---|---|
| G1 | 基础额度**每天 60 分钟**，不随星期变；周末的 150 = 60 + 做题上限 90 | `Limits.dailyMinutes` 不动，不加 `weekendMinutes` |
| G2 | 答案**随题下发**（选 i），拆包可见可接受 | 接口 `/v1/quiz/next` 带 `correct`；本地预判只做界面 |
| G3 | **ES256** | `server/tools/genkey.py`，公钥进 APK |
| G4 | 每天 **04:00** 换日，**整机统一** | `ParentalStore.dayKey()` 一处，见 PARENTAL.md「数据」 |
| G5 | 科学**不入库** | 只做语数英 |
| G6 | 配对码去掉易混字符，**保留大小写**（理由是防穷举撞库） | 见下 |
| G7 | 周报**不做推送**，H5 实时可查本周数据 | 去掉 `report` 的推送通道 |

**G6 的字母表**（这是穷举防线的一半，另一半是限速）：

```
abcdfghjkmnpqrstuvwxyz   去掉 l o i     (23)
ABCDEFGHJKLMNPQRSTUVWXYZ 去掉 I O       (24)
23456789                 去掉 0 1       (8)
```

55 个字符 × 6 位 ≈ 2.8×10¹⁰。**光靠大小写挡不住穷举**，真正的防线是三条必须一起做的限速：

1. 配对码**10 分钟**过期，只在电视上显示；
2. 同一个设备连续 3 次输入错误 → 这个码立刻作废，电视端要点「重新生成」；
3. H5 侧按来源 IP 限速：每分钟 5 次、每小时 30 次，超了直接 429。

大小写保留的代价是手机上容易输错（自动大写、看不到自己输的是大写还是小写），所以输入框**不自动大写、不自动纠正**，并把「区分大小写」写在提示里。这是户主明确要的取舍，别在后面「优化」掉。

### 13.2 与原设计不同的四处

1. **`cryptography` 换成自写 `es256.py`**。本机 pip 装不上（需 Rust 工具链）。代价是 300 行需要自己保证正确，
   补上了 `tools/interop_es256.py`：我们的签名 openssl 能验、openssl 的签名我们能验、密钥双向可读、
   翻转一位必须失败。Android 的 `SHA256withECDSA` 就是同一套 X9.62/DER。
2. **不用 FastAPI**。一个进程四条路由，`http.server` 足够，少一个要守护的进程。
3. **知识点树用 JSON 不用 YAML**。装不了 PyYAML；树本来就是脚本产的，不需要手写注释。
4. **去重窗口从"30 天全局"改成"7 天同题"**。原设计 30 天，但三天就能把单单元的题抽干——
   §6 的出题池已同步改成三层（当前单元 / 前两单元 / 错题）。

### 13.3 实现时发现的三个真问题

- **`3/4` 会被判错**（已修）。等价答案原先从小数化的显示值反推，导致 0.75 存在而 3/4 不存在。
  现在分数与小数两种写法都必进 `question_answer`。这是"孩子写对了却判错"，属于最不能接受的一类 bug。
- **填空题答案没随题下发**（已修）。G2 选了"答案下发"，但第一版只给选择题带 `correct`，
  填空题没有——本地预判分对填空题等于不存在。
- **英语干扰项与题干无关**（已修）。`past_simple` 原先从一个固定错误词表里抽，出现"用 fly 填空，
  选项是 doed / buyed"。改成按该动词本身生成规则化错误形式。

### 13.4 仍然是假的

- **题库**：86 题、模板生成、18 个知识点。够走通链路，不够给孩子做一周。真实题库按你的决定另行探索。
- **知识点树**：`verified=false`，三科都没和 OCR 结果核对过。湘少版 2026 秋是 10 单元新版
  （Unit 2 已从 Katie 改名 Beibei），旧版 12 单元——这种差异只能靠 OCR 拍板。
- **接口没有设备鉴权**，`device_id` 直接放请求体。签不出票，但能烧别人的次数。**P2 没做这件事**（P2 做的是电视端），
  它现在是整个方案里最大的洞，且只有 H5 的配对流程能顺带解决。

### 14.5 release 包里的两件事

这两条都只在本机查过，但都是**只在 release 才会咬人**的那一类：

1. **`res/raw/keep.xml` 必须存在。** CA 是用名字打开的（`getIdentifier("quiz_ca", "raw", …)`），
   这样没有证书的 checkout 也能编译。但名字不是引用，`isShrinkResources = true` 的 release 构建看不见它，
   随时可能把文件裁掉。症状是"release 专用"的一句「服务器的证书不对」——debug 包永远复现不出来。
   现在用 `tools:keep="@raw/quiz_ca"` 钉住；`aapt2 dump resources` 里 `raw/quiz_ca` 仍在（0x7f0b0002）。
2. **离线构建 release 要跳过 lint**：`-x lintVitalStandardRelease -x lintStandardRelease`。
   否则会卡在 `lint-gradle` 的传递依赖（`groovy:3.0.22`、`kotlin-reflect`）没有缓存，报的是一串
   和本功能毫无关系的 "No cached version"。

顺带核查过的一致项：`server/local/tls/ca.pem` 与 `res/raw/quiz_ca.pem` 指纹相同；
`ticket-signing-key.pem` 推出来的公钥与 `local/quiz.properties` 的 `publicKey` 逐字节相同；
release 的 `BuildConfig` 三个 `QUIZ_` 字段都在。

### 15.2 写的时候才定下来的六件事

1. **配对码不显示在锁屏，只在家长设置页**（`docs/PARENTAL.md` 已同步）。锁屏是孩子天天看的地方。
2. **`/v1/pair/renew` 必须沿用同一个 `device_id`。** 换新码如果顺手换 id，今天的三次机会、已得的 90 分钟、
   以及手机那边的绑定会一起留在旧行上——家长只是等过期重开一次，账就清零了。`pair()` 只在从没登记过时建新 id。
3. **心跳里 `used_ms` 是"上报"不是"累加"。** 电视发的是当日总数，漏一次不缺、重一次不涨。
   设计成增量的话，重传与补发都得另做一套去重。
4. **"最后写的赢"要版本号相等才采纳电视的值。** 电视比手机旧时，心跳里带的是它自己那份旧数；
   照着写回去会把家长五分钟前改的设置抹掉，而且看起来像"改了没生效"。`_take_tv_settings()` 只在
   `posted_version == current.version` 时才接。
5. **第一次心跳会把电视的现状变成"配置 v1"。** 服务端此时还没有 `device_config`（版本 0），电视也报 0，
   两个 0 相等、数字不同（电视是 0/30/20，服务端默认 60/30/20），于是按"电视改过"处理，落成 v1 并审计为 `tv`。
   随后电视自己拉到 v1、日志打 `config v1 applied`——一次没有变化的应用，但语义是对的：库里的值从此以电视为准。
6. **解绑只解手机，不吊销电视。**（2026-11-12 上机后改的）`/v1/h5/unpair` 原来顺手写了 `revoked_at`，
   看着像"这个手机不再有权限"，实际是把**电视**一起报废：出题、心跳、拉配置全部 403，而 `bound_at` 还留着，
   设置页照旧显示「已连接」，配对页于是永远不再发新码——家长从此既绑不上也用不了。现在只清
   `token_hash` 和 `bound_at`；`revoked_at` 留给"这台电视退役了"。
7. **换手机的路放在电视上，不放在服务端。**（2026-11-12 补的，见 15.6）已绑定的电视拿不到新码是对的——
   否则知道 `device_id` 的人就能把家长手机顶掉。但家长丢了手机也得有条路，于是这条路由家长密码把守：
   电视本地丢掉旧登记、重新登记。服务端因此一行没改。

### 15.3 怎么验的

- `server/tools/acceptance.py` 加了 P3 一组：配对成功 / 码错 / 过期 / 连错三次锁十分钟 / 限速 / 续码 / 配置版本 /
  错题本 / 周报 / 解绑（4 条）。**48/48 通过**（`.venv/bin/python`，需要 sympy）。
- 页面用真实 Chrome 跑（Playwright 无头，手机尺寸 390×844，`https://192.168.31.83:8443` 忽略自签证书）：
  没 cookie → 配对页；错码 → 红字「码不对。对着电视再看一遍——大小写也要一样。」且码还在；对码 → 主页面；
  刷新 → 仍是主页面（cookie 生效）；四个 tab 与暗色都看过。
- 两处照原样会很难看的，都是拿真数据才看出来的：
  - 电视还没报过数时「今天还剩」的大数字是 `—`，44px 把破折号画成一坨黑条。改成把「电视还没报数」这句话
    本身当标题（30px、次要色），下面一行解释。
  - 周报的柱状图**整块空白**：纵轴峰值取的是「当天已看与做题所得里较大的那个」，而柱高画的是已看；
    那天已看 1.5 秒、做题得了 30 分钟，1.5 秒 ÷ 30 分钟 = 0%，柱子高度 0。峰值改成取自**真正在画的那条序列**，
    再给 30 分钟的地板（一次通过就是这个数），并让任何非零值至少 3% 高——现在那天是一小截柱子，不是空白。

| 18:44:5x | 关掉配对页回到设置，「手机配对」那行从「未连接」变成「已连接」 |

两个只有真机才会露出来的点：

- **已绑定就不给第二个入口。** `prepare()` 先问服务端有没有绑过，绑过就只显示状态；要换手机得先在手机上「解绑这台手机」，
  电视下一轮才重新发码。这是有意的（`PairingPage.kt` 注释写了：配过的电视不该再递一把钥匙），但页面上没有一句话
  告诉家长「换手机请先在旧手机上解绑」——现在只有在文档里。要不要加一行字，等你定。
- **期间唯一一次异常是人为的**：验证到一半电视回了桌面，`Overlay.Parental` 被 `onHomePressed` 清掉（按 Home 就会这样，
  不是 bug）。重开后「每日观看时长」已经是 **0 小时 40 分钟**，说明配置落的是存储、不是页面回显。

### 15.5 仍然是假的

- **断网**：电视连不上时 `quiz: sync skipped (offline)` 只写日志、不改任何状态，这条只有单元测试。
- **错题本页面**：这台电视今天没有错题（1 组全对），所以真机上看到的是空态；带题干/答案/解析的卡片
  只在验收脚本的种子数据里出现过。
- **解绑确认框是浏览器原生 `confirm()`**：iOS 会把域名顶在对话框标题上，安卓上是系统灰框。能用，只是不算体面；
  换成页内弹层是外观问题，不是功能问题。

### 15.6 「换一台手机」，以及真机抓到的第一个界面 bug（2026-11-12 19:58，`guard` 1.70-88）

按 15.5 之前记下的死角补的：已绑定时配对页多一个「换一台手机」，过了家长密码才会看到它；点了以后电视本地丢掉
旧登记（`device_id`、配置版本、已绑定标记），重新登记拿新码。服务端一行没改——`/v1/pair/renew` 仍然对已绑定的
电视回 409，因为"知道 `device_id` 就能顶掉家长手机"是比丢手机更坏的事。

第一次点它就露了一个 bug，而且是**只在真机上才会露**的那种：

- 19:30:42 点「换一台手机」，电视上出现的不是六位码，是 **`01M77RCDWD`**——十位，ULID 的前缀。
- 原因：`QuizClient.pair()` 返回的是 **device id**（它顺手把这台电视登记进出题系统），只有 `QuizClient.renewPair()`
  返回码；而 `prepare()` 把两者的返回值都当码用。这条分支只在"这台电视第一次登记"时走，而它此前一直有 `device_id`
  ——六格码的页面从来只走 `renewPair`，所以从验收脚本到浏览器截图都没碰到。
- 修法不去动 `pair()` 的返回值（`fetchGroup` 拿它当 device id 用），改成两个调用之后统一从 `QuizVault.pairCode()`
  读码：两个调用都已经把码写进那里了，读存储比值对返回值少一处能对不上的地方。
- 19:56 装 1.70-88 复验：已连接 → 换一台手机 → **`CBQaHz`**（六位）→ 手机输码 → 已连接：Aerial TV；
  库里长出一行新的 `01M77SYV6J…`（19:58:14 建立、19:58:30 绑定），旧行原样不动。

代价（写在这里，也写在 `docs/PARENTAL.md`）：新行当天计数从零——手机页会先看到默认的 60 分钟预算、
0 次通过，直到下一次心跳把电视真正的设置（这台是「不限」）写回去。换手机一年一次，这个落差可以接受；
不能接受的是"没有任何入口"，那才是之前的状态。

顺带一句给以后的自己：这一轮安装被 TCL 多屏互动拒了两次，报「无法下载或安装」，原因不是签名也不是版本号，
是 `adb reverse tcp:8765` 在换设备连接时被清了（`adb reverse --list` 是空的）。重推前先看一眼它。

### 15.7 每日上限多了一个 1 分钟档（2026-11-12 20:30，`guard` 1.71-89）

验收「额度用完 → 锁屏 → 去做题 → 换到时长 → 自动放行」这条链，以前得先真放一刻钟视频把额度耗掉。
分钟档在 15 分钟下面加了一格 **1 分钟**（`15 ← 1 ← 不限`），一分钟就能撞到锁屏。

改了三处，前两处是同一个规则的两个入口：

| 位置 | 改动 |
|---|---|
| `ParentalStore.Limits.withDailyMinutes` | 分钟档在一小时以内走 `0 / 1 / 15 / 30 / 45`，一小时以上回到 `0 / 15 / 30 / 45`，十二小时只剩 `0`；按小时时 1 分钟被丢掉（1 小时 1 分是两个档位都推不出来的数） |
| `server/web/app.js` | 手机页同一步进：`15 → 1 → 0` 往下、`1 → 15` 往上、`不限 → 15`（不从 1 起步）；两端的置灰判断也按新档算，否则停在 1 分钟时「−」会被误锁 |
| `docs/PARENTAL.md` | 设置项表与一段说明（为什么留这个档、为什么只在一小时以内） |

真机（TCL 192.168.31.19）：

- 20:25 家长设置里把每日从 15 分钟按到 **0 小时 1 分钟**，界面正常（两段都在，分钟段 68dp 放得下「1 分钟」）。
- 20:26:56 用 `--ei parental_watch_min 1` 喂一分钟（不真放视频）→ `state: DailyLimit`、`dailyBudget 60000`、`dailyUsed 69565`；
  锁屏写「今天已看 1 分钟，上限 1 分钟。」
- 20:27–20:29 走完五道题（古诗两句、分数两道、英语一道）**5/5** → 「今天多了 30 分钟」→ 点「继续观看」锁屏自己退掉，
  状态回到 `Normal`，`dailyBudget 1860000`（1 + 30 分钟）、`dailyExtra 1800000`，日志 `quiz: ticket … spent, +30 min of 30`。
- 收尾：每日改回「不限」（分钟段消失、只剩一个「不限」段），重启应用让心跳把 `daily_minutes: 0` 推上去
  （`config_audit` 记 `source: tv`），并把今天那份测试计数清掉（`parental_reset` + 服务端 `daily_state`/`quiz_session`）。

手机页另起一个临时库（8444）用真实 Chrome 验的，不碰电视上已绑定的那台手机：
`60 → 45 → 30 → 15` 时「−」可用；`15 → 1` 存下 `daily_minutes: 1`；`1 → 不限` 后「−」置灰、存下 0；
从「不限」按「+」回到 15 分钟而不是 1 分钟。220 条单元测试绿（新增 `belowTheFirstQuarterSitsAMinute`、
`theMinuteDoesNotComeUpIntoTheSecondHour`）。
